# SLG 发布边界与战斗调度

后续交付脚本已完成新版单制品 K8s 闭环验收，见 [交付与换机接续](delivery-handoff.md)。本文末尾“本轮未重建镜像”描述的是版本路由改动当时，不代表后续流水线未验证；双版本制品共存仍未实测。

## 先看部署关系

- 登录服务独立一组；各区服的 Gate、世界、玩家服务和副本管理独立部署。这是目标拓扑，不表示这些 SLG 业务已经实现。
- 战斗服务独立部署。区服知道共同的战斗服务入口，不配置 `battlePoolId`，也不固定绑定执行节点。
- 现阶段复用 BattleManager 作为统一入口和调度者，不再增加一层只做转发的服务。
- 同版本战斗执行节点扩缩容不停止接单中的其他节点；版本更新允许维护。世界、Gate 等有状态服务另行设计，不能套用计算节点缩容。

## 一场战斗如何找到节点

请求包含 `realmId`、`battleId`、`logicVersion`、`configVersion` 和冻结的计算输入。

1. 管理器以 `(realmId, battleId)` 查原任务。相同内容和版本重试返回原状态，改变内容或版本返回 `conflict`。
2. 新任务只有存在存活、未排空且两个版本完全匹配的节点时才受理。节点忙时可以排队；没有兼容节点返回 `unavailable`，不创建记录。
3. 空闲节点只领取与自身版本匹配的任务。不会因为另一个版本的任务排在队头而阻塞可执行任务。
4. 执行节点再次检查两个版本，才调用生成的 NativeOps 委托 Rust；不能绕过管理器让旧节点计算新规则。
5. 调用方以相同区服和战斗编号查询结果，回执包含来源、逻辑版本、配置版本及执行节点。

`realmId` 只划分任务身份，不决定去哪一个池。例如一区、二区可以提交相同 battleId，各自得到自己的结果；两个区服的任务也可以先后由同一个节点执行。

当前仅为可信隔离实验：realmId 由测试调用方提供，**不是认证身份**，不能据此宣称跨租户安全隔离。正式接入时必须由认证后的服务身份限定可操作区服，管理命令也需独立授权。结果目前是查询回执，不是已经实现的 PlayerHost 推送或持久结算。

## 版本从哪里来

手写 `validation/battle/modules/battle/src/model/BattleRelease.ts` 定义该制品的不可变能力：

```text
logicVersion  = lcg-v1
configVersion = fixture-v1
```

这是确定性 LCG 计算夹具及其固定约定，不是真实兵种/技能配置。节点注册和执行校验引用同一份 Model 常量，不从部署环境变量随意声明能力。正式规则变更需连同实现、配置、版本、验收一起发布，不能只改版本名字。配置版本当前是严格相等的标识，还没有实际配置包哈希校验和分发。

新旧战斗规则可以注册在同一管理器下，前提是**管理器、执行端和调用方的 RPC 协议兼容**。规则版本路由不解决 protobuf/SDK 或管理器账本升级兼容。

## 维护与缩容

- 增加同版本节点：启动 → 就绪 → 注册能力 → 接单。
- 移除节点：停止接新单 → 已有战斗完成、结果交回管理器 → 确认排空 → 停进程/Pod。
- 更新规则的目标流程：准备并验证新制品 → 新版本节点注册 → 区服维护并收尾旧任务 → 区服使用新版本标识发起任务。旧版本仍有调用方时保留旧节点。
- 已受理任务失去兼容节点后保留排队，不降级到其他版本；当前没有等待超时或自动补齐该版本节点，需要人工恢复兼容容量。未受理的 `unavailable` 不表示未来一定会有容量。
- 在途任务失联后仍沿用 `unknown`，不直接重新计算。代码回退也不代表持久数据可以回退。

后两类发布流程目前不是自动化发布平台；没有实现区服维护开关、认证、分版本容量策略或多管理器高可用。

## 修改与验证入口

在 SLG 包目录执行：

```powershell
npm.cmd run battle:test
npm.cmd run battle:build
npm.cmd run battle:verify
```

手写：BattleRelease/BattleState、Hotfix 的 Input/ManagerSystem/HostSystem、薄 Handler，以及 `proto/`。生成：协议锁（显式更新）、服务端协议、TypeScript SDK、Native 和构建产物，均不得手改。

本次为协议升级：缺少 realmId 或版本的旧请求会被拒绝，必须完整重建并维护更新管理器、执行节点和 SDK，不能热更旧进程。K8s 镜像须重新制作；现有旧练习不会因源码修改自动升级。

混合版本路由由实际 Hotfix 配合模拟传输做单测；真实本地进程验证同一制品下的跨区隔离、版本拒绝及 TS→Rust。尚未进行新旧两份不同制品共存的 K8s 发布验收、故障/长稳或数据库结算验证。
